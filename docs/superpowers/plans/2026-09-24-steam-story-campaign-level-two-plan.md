# 《等等贝贝吧》Steam 品质升级、连续剧情与第二关执行方案

日期：2026-09-24。状态：网页版两关试玩里程碑已实施；Steam 包装、手柄、动画重制与外部试玩仍待后续工作。

本方案以本地 `dd90f1b` 为检查基线，结合现有源码、自动化模拟、Edge 浏览器检查和同类游戏官方资料制定。第二关、短剧情与四张衔接背景现已制作成 GitHub Pages 网页试玩内容；Steam 安装版延后，手机网页版继续兼容。

## 1. 推荐产品方向

定位为「有故事的双人角色追逐平台游戏」：玩家控制贝贝，读懂路线、把握跳跃和冲刺，利用道具追上孟培杰。区别于普通跑酷的重点是两个人的互动、上中下层路线选择和每关之间连续发生的故事。

近期先做两关完整试玩版：第一关负责认识人物、学会操作；第二关证明路线选择和道具有持续变化。用这两关验证操作、动画、安装版和存档后，再扩展正式版。两关约数分钟的熟练通关内容，适合 Demo，不把它包装成内容充足的正式完整版。

保留原生 JS + Canvas 2D 和 ES modules。网页核心仍可直接运行；Steam 安装包单独增加桌面包装流程。默认自动前进、向左回头、按住向右冲刺、跳跃/二段跳、下 + 跳穿台、三颗心和 85% 追上窗口继续作为基础设计。难度主要来自路线组合和决策，不逐关提高基础跑速或改变熟悉的跳跃弧线。

## 2. 本次检查：已经有什么、还差什么

### 2.1 已验证基线

- `node --test`：104 项通过，0 项失败。
- `node tools/level-bot.mjs`：理想路线 128.8 秒、88.5% 处追上，无跌落；自动跳跃机器人到 58% 失败；零输入到 7.5% 失败。这是机器人行为，不能换算成人类玩家通过率。
- 本地 Edge：1366×768、390×844、844×390 三种视口未出现页面异常或资源请求失败；暂停后的 Canvas 两次截图相同。
- 已有：短跳、二段跳、100ms 离台宽容、120ms 提前按跳缓存、扫掠落脚、三颗心、检查点、篮球投射物、暂停、按区域加载 WebP。
- 未验证：实际手柄、Steam 安装包、Steam Overlay、真实手机性能、低配电脑长时间帧率；本次也没有亲自通关竞品，竞品结论来自官方产品资料和开发者文章。

## 3. 同类游戏借鉴：落到本项目的具体做法

1. **Super Mario Run：操作少，路线和跳跃时机有层次。** 官方描述的核心是自动前进与点按时机，并用短关卡组织内容。我们保留简洁输入，把乐趣放在上下路、收集目标和短段组合，每 15～25 秒给玩家一个新的判断。[Nintendo 官方介绍](https://supermariorun.com/en/)
2. **Celeste：宽容的输入帮助玩家准确表达意图。** 开发者介绍了离台宽容、跳跃缓存与边角修正等做法。我们保留已有前两项，先修快速点按不一致；边角修正只对确实存在的碰头场景小范围试验，不引入穿墙或吸顶。[开发者文章](https://www.mattmakesgames.com/articles/celeste_and_forgiveness/index.html)
3. **Rayman Legends：关卡行为与节奏相配。** Ubisoft 官方介绍包含音乐驱动的关卡。我们借鉴“教学、连续动作、喘息、高潮”的组织方式，让提示音与机关预警协调；第二关仍以可见机关为准，不要求玩家听音乐才能通过。[Ubisoft 官方介绍](https://news.ubisoft.com/en-us/article/mqXBE5x8Kcn2NzNmrJclL/rayman-legends-definitive-edition-out-now-on-nintendo-switch)

以上是设计原理参考。人物、美术、音乐、地图和台词使用自己的素材；不移植其他商业游戏的角色或关卡。

## 4. 连续故事：让每一关都有去下一关的理由

### 4.1 推荐故事设定（原创虚构，可作为正式创作底稿）

故事暂名「日落前，等等我」。地点是一座大学与河岸老街相连的小城；校园节当天，两人约好在钟楼敲响闭幕钟前，赶到观景台拍一张合照。

孟培杰熟悉近路，一兴奋就往前跑；贝贝想赶上他，也想好好看看沿途的活动。一路从“你怎么又不等我”，走向“你带路，但要记得回头”。两人的关系保留亲近、轻松的表达，不擅自把虚构经历写成真实往事。

剧情服务追逐：孟的速度变化有台词和动作原因，路线会汇合，道具可以帮贝贝赶上，也可以帮两人打开近路。打一下、坐地哭的既有演出保留为夸张漫画式互动，失败不需要编成悲剧。

### 4.2 第一关改造：「校门口，说好的等我呢」

- 开场：校门公告牌显示“校园节 · 日落合影”。贝贝拿着相机，孟指向远处钟楼。两张短对话即可交代目标。
- 示例台词：贝贝：“说好一起走的。”孟：“我先去看看近路！”跑起来后再出现贝贝：“你倒是等等我呀！”
- 第一关仍经过校门、球场、银杏路、湖畔、天桥，场景明确属于同一校园；背景中的钟楼逐渐变大，时间从下午推进到傍晚。
- 篮球场教自动踢球，银杏路教分路，湖畔教移动平台和危险预警，天桥做复习与追上。原有每区相近的节拍按这些教学任务重排。
- 胜利：贝贝轻拍孟：“没心眼，不等我。”孟回头指出天桥下的河岸旧街：“知道啦，下一段你选路。”镜头显示第二关入口。
- 下一关再次追逐是两人约好的赶路挑战，有开场互动承接，不用“刚抓到又无缘无故逃跑”重复推动剧情。
- 失败：贝贝坐地哭，孟在远处回头；给出实际失败原因与快速重试。失败动画可跳过，重试不重复播放整段开场。

### 4.3 第二关剧情：「沿河旧街 · 钟楼下等我」

- 起点就是第一关天桥的另一端；远处同一钟楼、河流方向、夕阳方向完全一致。
- 中途发现通向钟楼的小桥被送货台挡住。贝贝用篮球撞开机关，孟在前方停下看一眼，配一句“这条近路还得靠你”。
- 上层是店铺露台和装卸平台，下层是安全一些但绕行感更强的河岸石道。两条路线在钟楼广场前汇合。
- 本关结尾在钟楼下追上，两人看到通向坡上花园的标牌，接第三关。终章的观景台合照暂不提前兑现。

### 4.4 后续关联路线（初步内容方向，逐关验证后扩展）

| 关卡 | 地点和故事推进 | 主要玩法学习点 |
| --- | --- | --- |
| 1 | 校园到天桥，建立“等等我”的约定 | 跳跃、冲刺、篮球、基本分路 |
| 2 | 河岸旧街到钟楼，两人开始配合找近路 | 移动货台、篮球开机关、上下换路 |
| 3 | 钟楼后坡道到花园，贝贝开始主动带路 | 弹簧与分段落点，旧机关组合 |
| 4 | 阵雨中的温室外廊，绕开积水 | 明确预告的周期机关与快慢选择 |
| 5 | 校园节后勤区，赶在推车队前穿过 | 移动挡板、坠箱的组合与等待窗口 |
| 6 | 山坡栈道，看见观景台但路线变窄 | 连续平台、横风；充分提前展示落点 |
| 7～9 | 活动街区、山腰连廊、最后上坡 | 已学机制重新组合，每关至多一个新重点 |
| 终章 | 日落观景台，最后一段先追上、再并肩入镜 | 复习高潮；结尾孟停下来等贝贝 |

不要求故事关逐关持续高压。全局难度上升，每关内部仍有安全教学和喘息。首个正式版建议先以 8～12 个有区别的关卡估算内容规模，实际定价和宣传时长以陌生玩家测试为准。

### 4.5 剧情呈现规则

- 关前约 10～20 秒、关后约 8～15 秒，默认可一键跳过；看过的剧情可自动跳过并在关卡菜单回看。
- 跑动台词尽量 8～12 个汉字、约 1.2 秒；更长的话放在安全停顿处，模拟暂停、玩家按键推进，不能逼玩家边跨坑边读。
- 必要教程出现于安全实体地面，不覆盖角色脸、危险预警或落点；台词之间设冷却，AI 模式变化不立即连续刷屏。
- 收集照片碎片/校园节印章作为可选支线，不收集也能过关；收集结果只丰富相册或结尾文案，不改变必要平台是否存在。
- 剧情数据记录 speaker、text、trigger、seenKey、nextScene；故事状态和物理更新分开，跳过演出不会跳过机关初始化、奖励或解锁。

## 5. 第一关与第二关的美术连续性

### 5.1 世界风格与背景调整

推荐统一为「暖色日漫插画的大学与河岸小城」。允许有漂亮的历史建筑，但移除当前校门背景里与其他区域不相容的巨大魔法城堡、悬空城市等元素。第一关和第二关沿用相同的米色石材、深色铁艺、红棕屋顶、校园节旗帜和钟楼轮廓。

先做一张世界关系草图：校门 → 球场 → 银杏路 → 湖畔 → 天桥 → 河岸街 → 钟楼。它决定左右行进方向、河岸位置、钟楼远近和太阳位置。之后各区域出图都引用这份设定，不让每张图各自创造世界。

第一关五区调整清单：

| 区域 | 背景要表达什么 | 与下一段的连接 |
| --- | --- | --- |
| 校门 | 同一大学的入口，节日横幅，下午光照 | 远处出现球场灯架；钟楼位于同一方向 |
| 球场 | 同色校园建筑、看台、节日活动痕迹 | 背后可见银杏路，不突然切到另一座城 |
| 银杏路 | 林荫与校园旧建筑，保留同一钟楼轮廓 | 树间开始露出湖水 |
| 湖畔 | 河湖相接、校园施工围挡、天桥引桥 | 天桥逐渐进入中景 |
| 天桥 | 沿河旧街可见，光照逐渐转暖 | 第二关第一屏复用同一桥头地标 |

### 5.2 出图、图层和地面标准

- 初期沿用逻辑画布 1280×540、基准地面 y=510；背景目标 2560×1080。改变出图不改物理坐标。桌面全屏先按比例放大，不能横向拉伸人物。
- 背景负责远景与环境；真正可站的地面、平台边缘和道具由可碰撞实体层绘制。少画容易被误读成平台的强水平高亮线。
- 使用远景、中景、少量前景分层；遮挡只在不会影响路线判断的位置。禁止再次叠加穿过角色的路灯/栏杆虚影。
- 可平铺层逐张验收左右接缝；地标用有限长度的独立段，不宣称任何生成图天然无缝。
- 第一关出口和第二关入口做一组并排验证图，检查桥栏高度、石材、光照、河流与地标位置。
- 地面/高台材质改成同套石路、木平台、金属货台的端头/中段/转角模块；危险台与安全台用轮廓、图案和预警区分，不能只靠颜色。
- 角色外观沿用当前服装；孟培杰每个姿势保留眼镜。两人加清楚但柔和的轮廓分离，背景局部降低对比度，优先让可玩对象清楚。
- 美术顺序：一张风格样板和游戏截图合成 → 第一关桥头/第二关入口对照 → 两关必要背景 → 道具平台 → 其他关卡复用。先验证再批量出图。

## 6. 第二关的可执行关卡草案

### 6.1 总体参数

- 稳定 ID：`journey-02`；显示名称「沿河旧街 · 钟楼下等我」。旧数字 ID=2 继续对应校园入口练习，不直接占用。
- 玩法长度初值 18000 世界单位，世界绘制延伸至 18500；熟练游玩目标约 100～150 秒，含谨慎操作的初见约 2～3 分钟。这是设计目标，需通过模拟和试玩修正。
- 85% 开窗对应 x=15300；最后追逐区始终保留实体地面，最后约 600px 不放新的致命机制。终点 x=18000 放在明确地标处，胜负检测顺序为先判有效接触，再判越过失败线。
- 三颗心；约 4 个检查点，建议安全区 x≈4200、8500、11600、15100。最终坐标以实体地面与危险周期检查为准，出生区前后留反应空间。
- 高路约覆盖 35%～45%，最多同时呈现三层。必走线路不超过两层连续复杂操作；第三层是可选挑战。
- 基础跑速先保持 150、冲刺 240。第一轮用现有跳跃参数，但先修快点跳输入。跳跃可达性由实际模拟测得，不能只套 v×t 理论极限。

### 6.2 七段手写节奏

| 区间 | 玩家体验 | 路线、道具与危险 |
| --- | --- | --- |
| 0～1800 | 桥头承接、轻松教学 | 连续石路；500px 内给第一颗能量；一组低移动台，下面有安全地面；展示篮球机关的反馈。 |
| 1800～4300 | 熟悉移动货台 | 两次节奏不同的横移平台跨越；落点先可见；主路可跳过短坑，上路多币；本段只要求一种新判断。 |
| 4300～7200 | 第一次明显分路 | 下路宽、奖励少；中路移动货台 + 小挡板；上路露台有能量与一枚纪念印章；各路在安全区汇合。 |
| 7200～8800 | 喘息和剧情推进 | 休息广场、检查点与补给；可选一句短对话；第一次篮球开机关的安全复习，漏踢仍能走主路。 |
| 8800～11700 | 主动上下换路 | 上层预警塌陷、下层稳定；教下 + 跳落到下一层；危险预警时间足够，落点不放贴脸伤害。 |
| 11700～15300 | 已学机制的小高潮 | 移动台、挡板、塌陷按先后组合；同时最多两种需要判断的危险；用篮球打开一条奖励近路，失败有较慢的可通行路线。 |
| 15300～18000 | 开窗与追上 | 路线汇合；明显的能量/篮球机会；孟有可见疲劳或回头动作，不能瞬移；追上后进入钟楼短演出。 |

关卡图先用碰撞体和编号制作可玩的草图，路线上需标出起跳点、落点、默认走法、奖励走法、资源、检查点和 AI 出口，不能先铺漂亮平台再猜能否通过。

### 6.3 本关的新内容与预算

只增加一个主要交互：**篮球击中机关，打开一条近路**。移动货台是现有移动平台的主题化和编排，不另写一套物理。

- 篮球：沿用自动向前踢。普通球优先处理前方机关或孟，按数据明确指定交互目标；不突然夺走玩家原本瞄准孟的球。命中机关后给出按钮压下、门升起、短音效；球只结算一次。
- 机关：按下后本次尝试内保持开启，避免玩家到门前突然关门。主路不依赖一次性球才能继续；检查点恢复必须恢复一致的门状态和球状态。
- 道具初始预算：普通币约 40～60、能量约 10～12、篮球约 5～6、补心 2～3、纪念印章 3。数量用作布点预算，不机械均匀撒满地图。
- 能量初值每颗 +40、消耗沿用 24/秒。一条正常路线目标可拿到至少 6～8 颗，约支持 10～13 秒冲刺；容量溢出部分不计入有效预算。
- 终段主路单独安排补给；逐条计算当时的间距、可用能量、AI 速度与剩余路长。验证“不拿可选高路奖励也有可控获胜办法”，但不提供自动判赢。
- 纪念印章分别奖励探索、稳定操作和道具时机；挑战目标是“通关 / 收集齐 / 无伤”等独立记录。第一次通关不要求全部达成。
- 普通必经坑优先 60～150px；更大跨度只用于已验证的冲刺/二段跳奖励路线。移动台在整个运动周期内都有可等待或可退回的位置。

### 6.4 第一关难度顺带整理

- 先展示机制，再施压；第一关前 20～30 秒避免混合多个新机制。
- 替换五区近似重复的长地面节拍：球场突出篮球，林路突出分路，湖畔突出平台周期，桥段复习。
- 将过于接近坑边、看不到落点或直接堵住检查点的危险重新布局。
- 第一关结尾铺稳定追上区，修正终点处于坑中的问题；新第一关仍要通过原有追逐与生命回归。

## 7. 操作、动画和性能专项

### 7.1 操作手感

- 首先修同帧快速点击的跳高差异，再统一键盘、触摸、手柄的动作事件：按下、保持、松开、取消。不能只读每帧最终布尔值而丢失先后顺序。
- 默认操作保持既有习惯。手柄左摇杆/十字键控制方向，向右保持冲刺，A 跳跃，↓ + A 穿台，Menu 暂停；所有菜单可通过手柄完成，支持热插拔和重新映射。
- 增加按键提示随最后输入设备切换、死区设置、音量、窗口/全屏、画质和减少视觉特效选项。暂不加入震动，沿用用户之前删除震动的选择。
- 加速与转向需要匹配动作。可试验约 80～120ms 的冲刺加速过渡，但只有在短跳和路线回归通过后再调；必须第一帧有响应，不为了“平滑”加入明显输入延迟。
- 暂停/切后台/手柄断开时清输入；恢复前仍清一次。跳跃音效由实际起跳事件触发，而不是任何一次按键都响。
- 手机按键保持画面外；竖屏兼容，横屏优先。PC 只展示实际需要的键盘/手柄提示，不显示手机按键。

### 7.2 人物动画

- 当前 128px/轮、12 帧，在150速度下约14次换帧/秒，冲刺约22.5次；60Hz画面更新不等于有60张角色姿势。
- 沿用全身序列帧和独立距离相位，先把12个姿势做对。锁定肩、胯、头部比例、左右手脚关系和地面坐标；有必要时只补关键过渡帧，不靠堆帧数、叠图或模糊解决跳变。
- 两个人各自校准步幅；支撑脚在支撑期的后移速度要与地速相配。保留当前服装、脸、发型，孟的眼镜必须逐帧检查。
- 补齐待机/回头过渡、落地承重、打滑、倒地、拍打、剧情回头姿势。跑、跳、哭等动作共用锚点与身体比例；人物蹲低允许轮廓变矮，不强行拉伸到相同包围盒。
- 动画预览支持0.25倍、逐帧、左右翻转、普通/冲刺速度、基线、帧边缘检查。自动检测源矩形越界、透明安全边距与异常孤立组件；组件检测仅做候选提示，再人工确认发丝、衣角等合法细节。
- 支撑帧基线目标误差≤1源像素、单次支撑期脚滑目标≤4世界像素；这些是验收目标，需要录屏逐帧验证，现有 PNG 格式测试不能证明。

### 7.3 追逐 AI 与资源反馈

- 移除85%瞬间拉近和金币直接改位置的表现，用有上限的速度变化、停顿/受击动画和终段路线汇合表达。前85%依然不可追上，但通过提前规划逃脱保证人物不会已经贴在一起却无反馈。
- 孟在终段170的配置与贝贝150的常速必须重新一起标定；成功应能归因于冲刺、近路或篮球，不靠概率掷骰。
- AI 路线明确包含入口、落点、等待点、下台出口；门打开/关闭、平台塌陷时重新验证目标。以未来落点而非平台当前位置评估移动平台。
- 原有共享落脚求解器继续使用；每关每条 AI 路线都测跨坑、减速中跳跃、移动台不同相位及终段汇合。有效地面上不得悬空跑；卡住恢复应回到安全决策，不在画面内无提示瞬移。
- 篮球命中孟目前有25%倒地随机分支。建议统一为可预测的减速，若需要倒地则通过清楚的条件触发；用固定种子保留旧行为回归与对比，再迁移新规则。

### 7.4 渲染与性能

- 默认固定60Hz物理，与30/60/高刷新率显示解耦；保存前后模拟状态，渲染插值。碰撞、伤害、机关只读模拟状态；传送回档、暂停恢复时重置插值，避免拖影。
- 性能降级先降低粒子、背景装饰和分辨率倍率，再降低绘制到30FPS；不能只改变物理步长并继续全频绘图。若物理成为瓶颈，再按角色附近区段筛选实体。
- 不每帧对全关卡反复排序和查找：静态路线与平台ID索引在载入时建立；动态快照一帧生成一次，渲染、落脚和危险读取同一位置。
- 孟的实时 Canvas filter、重复渐变和频繁 HUD DOM 写入需要实测；优先将固定描边/亮度烘焙进资源、HUD 数值变化时才改 DOM。只优化测得的热点。
- 活跃资源用 manifest 管理；新关只加载自己的背景与道具，预取下一场景；原始大图与旧版本不进入Steam发货包。删除资源前检查引用并保留源素材归档。
- 默认60FPS；低档30FPS为明确可选/自动模式。高刷新率先验证插值、输入和动画相位，再提供120FPS选项，不承诺所有设备满帧。

## 8. 多关卡与剧情的数据结构

适度拆分现有大文件，新增内容不再复制整套游戏逻辑。建议职责如下：

| 模块 | 负责内容 |
| --- | --- |
| `levels/catalog.js` | 稳定ID、顺序、名字、前置关、nextLevelId、预览图、主题、剧情ID |
| `levels/journey-01.js` / `journey-02.js` | 每关手写路线、地面、道具、危险、检查点、追逐区与终点 |
| `levels/beats.js` | 少量已验证的教学/分路/机关组合片段；按关卡手写组合，不随机拼图 |
| `story/scenes.js` / `story/player.js` | 开场、收尾、区域短台词；播放、跳过与已观看记录 |
| `input.js` | 键盘/手柄/触摸转换为统一动作事件和保持状态 |
| `game-logic.js` / `pursuer-ai.js` | 模拟与AI，接受关卡参数，避免识别关卡编号的分支 |
| `render/` | 逐步移动角色、场景、道具绘制；外观调整不改碰撞状态 |
| `assets.js` | 图片/音频清单、加载、解码、重试与每关预取 |
| `level-progress.js` / `storage.js` | 进度与设置、版本迁移、网页版存储和桌面文件存储 |
| `desktop/` | Steam桌面壳、窗口、受限存档接口、打包配置 |

存档建议 `schemaVersion: 2`，按字符串关卡ID保存已解锁、通关、收集、最优记录与已看剧情。旧1映射第一旅程，旧2～6映射五个练习章节；旧第一旅程通关可解锁新第二关，练习第一段通关不能冒充完整第一关通关。旧存档保留备份，迁移重复执行不会重复发奖。

关卡数据校验包括必填字段、唯一实体ID、坐标范围、道具支撑面、检查点安全、机关关联和 nextLevelId 存在。添加第三关应只需新增关卡/剧情/素材数据与测试，不再改胜负主循环。

## 9. Steam 发布路线

### 9.1 技术路径

推荐先做一个 Electron Windows 桌面壳验证现有 Canvas 游戏：本地打包资源、离线启动、窗口/全屏、键盘手柄、存档。这样可以复用当前逻辑与素材；核心网页仍不需要打包器。Electron 自身需要打包流程，单独放在 `desktop/`。[Electron 官方分发说明](https://www.electronjs.org/docs/latest/tutorial/application-distribution)

先测性能和启动体验再确定发货方案；不把包装网页等同于完成Steam移植。生产渲染页面关闭Node集成、启用隔离，存档仅通过有限接口；本地资源使用适合ES module的协议与路径处理，不能靠开发服务器常驻。[Electron 安全建议](https://www.electronjs.org/docs/latest/tutorial/security)

存档使用用户数据目录中的文件，原子写入并保留备份；支持脱网重启、更新不丢档。浏览器localStorage与安装版存档不会自动互通，提供一次性的导出/导入或说明迁移边界。Steam Cloud和成就可在Demo稳定后接入；支持的功能以真正完成并测试的项目为准。

手柄输入与菜单先做完整，再配置Steam Input；后者支持配置不同输入设备，但不能替代游戏自身的菜单焦点、断连处理和按键提示。[Steam Input 官方文档](https://partner.steamgames.com/doc/features/steam_controller)

### 9.2 上架准备与产品节奏

- 先交付两关Demo，再通过试玩决定扩展哪些机制。建议至少邀请8～12位不熟悉项目的玩家，分键盘与手柄观察首次游玩，记录失败位置、误操作、读不清的地面和重复段落。
- 付费完整版的内容量、价格、支持系统与最低配置要在真实安装版测试后决定。首发先聚焦Windows；没有测试的macOS/Linux/Steam Deck不先承诺支持。
- 准备统一的封面、商店胶囊图、真实游戏截图、实机预告片、说明、操作提示和支持联系方式。商店截图和功能需反映实际发货内容。[Steam 审核流程](https://partner.steamgames.com/doc/store/review_process)
- 按官方当前要求，Steam Direct每产品100美元；初次发布流程涉及缴费后的30天等待、公开Coming Soon页面至少两周，并包含页面/构建审核。时间可部分并行，应在打磨Demo时准备，不能把上线日期只按代码完工估算。[Steam Direct](https://partner.steamgames.com/steamdirect)；[入驻流程](https://partner.steamgames.com/doc/gettingstarted/onboarding)
- 游戏使用AI辅助生成的玩家可见美术，需要按Steam内容问卷如实说明预生成内容；建立素材来源、制作方式、可商业使用依据的台账。人物以真实姓名/照片为原型的商业使用也应提前与本人明确。这是本项目实际发布准备项。[Steam 内容问卷](https://partner.steamgames.com/doc/gettingstarted/contentsurvey)

GitHub Pages继续作为网页试玩渠道。Git推送、Pages发布、Steam上传构建是三条不同流程，分别记录版本与验收结果。

### 10.1 自动化验收

- 保留当前104项测试的有效覆盖；涉及固定物理、确定性篮球、存档结构等规格变化时更新旧预期，不用旧测试锁死错误行为。
- 新增短按同一步/跨步、落地缓存已松开、输入取消与暂停恢复；按相同事件时间线在30/60/120渲染节奏下比较模拟结果。
- 每关、每条路线模拟起点、终点、普通/二段跳、低能量、移动台至少8个周期采样、受击后恢复。边缘风险处继续缩小时间采样验证，不能把有限采样当数学上的全周期证明。
- AI全程记录不合理悬空、无进度、无效支撑面、掉坑和位置不连续；区分正常跳跃腾空与异常悬停。
- 篮球机关：击中一次、打开持续、球过期、检查点恢复、先击中孟/先击中机关的优先级。
- 存档：旧档迁移、重复迁移、未知关卡记录保留、坏档回退、更新前后解锁不倒退。
- 剧情：首次播放、跳过、重试不重复、结尾只结算一次、读档后观看状态正确。
- 安装版：打包资源路径、离线冷启动、不同Windows用户名路径、存档权限与备份恢复。

### 10.2 视觉、体验和性能验收

- Windows实际安装版：1280×720、1366×768、1920×1080、2560×1440，以及125%/150%系统缩放；全屏、窗口、Alt-Tab、Steam Overlay、手柄拔插。
- 目标60FPS：记录设备、分辨率、画质、10分钟路线的帧时间分布；初定P95≤18ms、P99≤33ms，持续卡顿需定位。低档30FPS另测帧节奏，不能仅看平均FPS。
- 冷启动到可交互初定≤5秒（指定SSD测试机）；场景切换不得出现角色空白、旧模型回退或资源混用。内存目标在桌面壳样机测量后确定，不凭图片压缩体积推断解码占用。
- 角色慢放检查支撑、蹬地、腾空、反向、短跳、二段跳、落地与结算；截图通过不等于动作已通过。
- 手机保留390×844与844×390回归，按键不挡画面；真实手机验证单独记录。
- 每关至少一个视觉记忆点、一个可选捷径、一个明确喘息段；通关前玩家能说出第二关与第一关的区别。

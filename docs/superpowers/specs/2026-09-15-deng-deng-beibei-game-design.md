# 《等等贝贝吧》游戏设计规格

> 当前版本：2026-09-20。本文描述仓库现状与验收规则；早期的“两关低分辨率像素版”方案已被高清连续追逐与章节模式取代。

## 游戏目标

这是一款原创 2D 横版追逐跑酷游戏。玩家操控女生董贝贝，穿过校园、银杏林、湖畔施工区和黄昏天桥，追赶男生孟培杰。画面采用清晰的高清 2D 插画与角色精灵，不追求马赛克像素外观；经典平台跑酷只作为节奏参考，角色、关卡、美术与音效均为本项目内容。

## 技术与设备

- 原生 HTML、CSS、JavaScript ES modules 与 Canvas 2D；无框架、打包器、后端或第三方运行时依赖。
- 画布逻辑尺寸为 1280×540；根据设备 DPR 设置 backing store，DPR 上限为 2。
- 固定步长模拟默认 60 FPS；检测持续性能压力后降至 30 FPS，恢复后回到 60 FPS。
- 五张区域背景优先加载 WebP，保留 PNG 回退；按所在区域及邻接区域懒加载。背景按画布比例裁切，不变形，并叠加轻量的动态飞鸟、落叶等纵深元素。
- 角色视觉框统一为 60×80；跑步循环按行进距离推进，包含手臂与腿的摆动。贝贝有跳跃和哭泣动作；孟培杰保留眼镜并由独立 AI 驱动。
- 游戏界面、HUD 和结算按钮由 HTML 提供；跳跃可用键盘或点按画面。手机可通过 GitHub Pages 访问，但不同网络对 GitHub 的可达性不保证。

## 游戏模式与路线

主模式是一张连续 24,000px 的长地图，地面基准 y=510，终点坐标为 23,500。五个区域各约 4,800px：

1. 校园入口：教学跳跃、惊喜方块与基础危险。
2. 篮球场：篮球可自动踢向前方，命中会让孟培杰减速或短暂倒地。
3. 银杏林路：金币路线、香蕉打滑与巡逻障碍。
4. 湖畔施工区：施工箱、移动挡板、弹簧与施工危险。
5. 黄昏天桥：连续风区、终段高路与追逐高潮。

主页还提供五个单独章节，每章对应一个区域。完整旅程始终可玩；逐章胜利解锁下一章。章节、最佳进度、硬币、胜场与徽章保存在本机 `localStorage`，不上传服务器，也不跨设备同步。

关卡地面节奏由手写数据编排，依次安排教学、常规、加压、喘息和高潮；各区有不同坑宽与危险组合。高路是可跳上的可选捷径，提供速度收益与奖励。桥区另有弹簧接入的连续高路，孟培杰也会根据自己的位置选择该路线，而不是跟着贝贝同步跳跃。

## 操作与机制

- 贝贝自动向前跑。
- A / ← 减速并向后移动；D / → 消耗能量主动冲刺。拾取能量或顶到惊喜方块可补充冲刺资源。
- 空格 / W / ↑ 或点按游戏画面跳跃；支持二段跳、跳跃缓冲与短暂离台后的宽限起跳。
- 金币缩小追逐距离；触碰篮球会自动将球踢向前方；香蕉使贝贝打滑；弹簧台、加速垫、横风、巡逻障碍、施工箱、挡板和短暂塌陷平台要求不同应对。
- 掉坑后回到最近检查点并增加追逐距离；碰到危险、落后过远或跑到终点仍未追上会失败。

### 孟培杰 AI 与追上判定

孟培杰有自己的巡航、逃跑、减速、倒地与追逐状态，按时间节奏移动，并基于自身位置寻找高路。篮球命中会改变他的速度状态；他的跳跃和路线选择不读取贝贝的跳跃按键。

进度达到 85% 才开启终段追上窗口。开窗会把间距缩至最多 100px，**但不会直接判胜**；只有两人实际间距不超过 56px 才算追上。窗口开启后仍需玩家利用主动冲刺、能量、篮球和路线选择争取接触。抵达地图末端仍未接触则失败。

## 结局与反馈

- 失败时停止追逐，显示贝贝坐地哭泣动作、文案“贝贝跟丢了”，并提供“放弃”“再来一遍”“返回主页面”。
- 胜利时先播放贝贝轻打孟培杰、孟培杰倒地的短动作，再显示“贝贝追上了”和台词“没心眼，不等我”；可进入下一章、重玩或返回主页。
- 距离 HUD、孟培杰头顶距离、边缘危险提示、贴近速度线、能量条和短时嘲讽提供过程反馈。相机平滑跟随；不使用镜头震动。
- Web Audio 在用户开始游戏后解锁，以振荡器合成跳跃、落地、拾取、冲刺、命中、检查点和结局音效；声音不是胜负判定的唯一信息。

## 验收标准

- `node --test` 全部通过；当前为 78 项。
- `node tools/level-bot.mjs` 检查平台可达性、坑宽、区域节奏和理想/零输入路线；当前自动断言全部通过。理想路线模拟约 120.6 秒，并在约 85.4% 进度追上。该模拟不等于真人试玩结果。
- 页面使用本地资源，不依赖远程字体、第三方脚本或 API；WebP 不可用时可回退 PNG。
- 发布前仍需在真实浏览器和手机视口手动检查完整流程、素材加载与触控。此前本机浏览器自动化受权限错误阻断，尚不能声称已完成这项视觉实机验收。

## 发布方式

仓库使用 GitHub Pages 的静态托管目标，不需要构建。预期发布源是 `main` 分支根目录；仓库没有自动部署 workflow。向 `main` 推送后，Pages 是否更新取决于 GitHub 仓库设置和平台构建状态，需要在线确认。
